1. 为什么需要 AI 集群，为什么需要网络

单张 GPU 的显存、算力和输入输出带宽有限。当模型及其运行状态放不进一张卡、训练时间不能接受，或单机处理能力无法满足业务峰值时，需要多个加速器协同。单机多卡通过 PCIe 或专用互联形成 Scale-up；多台服务器通过网络形成 Scale-out；跨机房或数据中心协同常称 Scale-across。Scale-up 不一定局限于单机，具体互联域依产品而定。

集群不只是把卡的峰值算力相加。切分任务产生参数、激活、梯度及控制数据交换，节点还要读取训练样本、保存检查点、接受用户请求。网络速度、数据路径、拥塞和故障共同决定 GPU 能否持续工作。对于小模型或低并发业务，单机可能更简单、更经济；多机只有在容量、时间或可用性确有需求时才有价值。

2. 训练和推理：每一步使用什么硬件

2.1 训练一次迭代

数据先从存储经存储网进入主机内存，经预处理后送至 GPU 显存；GPU 完成前向和反向运算。多卡并行时，通信库组织梯度或激活交换，本机使用节点内互联，跨机使用网卡与计算网络；优化器更新权重，并周期性写入 checkpoint。数据预取、梯度分桶及通信计算重叠可以减少等待，但也会改变网络突发形态。

2.2 推理一次请求

阶段资源与数据流集群/网络影响
启动与加载模型权重从存储加载至主机内存、GPU HBM；CPU 启动服务与分词。启动时间、并发加载和存储吞吐可能是瓶颈。
Prefill输入 token 生成中间状态和 KV Cache；大批量矩阵计算占用 GPU 计算与显存。跨 GPU 的张量并行需要通信；长输入增加首 token 时间与缓存占用。
Decode逐步生成 token，反复读取权重和 KV Cache。显存容量/带宽及每步通信时延重要；并发和输出长度影响每用户速度。
跨节点 / 分离部署请求由业务网进入；TP、EP 或 Prefill/Decode 分离可能跨机交换激活、token 或 KV。路径和字节量由框架实现决定；并非所有推理都要求 RDMA，须实测。

主要业务指标包括首 token 时延 TTFT、后续 token 间时延/TPOT、请求成功率以及规定输入输出分布下的吞吐。不同负载、批量与并发之间不能只用单一 token/s 比较。[1]

3.1 Leaf-Spine、Rail 与 Plane

Leaf-Spine：端点连 Leaf，Leaf 上联多个 Spine；每对 Leaf 常有多条等价路径。它适合规模扩展，但是否无超售取决于接入和上联带宽、端口配置、故障状态及实际流量；并非所有拓扑自动无阻塞。Rail：按服务器内 GPU/NIC 编号组织亲和组，使相同编号设备优先连接同一组 Leaf；Rail 可以在高层互通，也可以独立。Plane：覆盖相关端点、彼此独立的并行网络；每个端点要有可用路径分别连接各 Plane。Rail 与 Plane 是两个维度，可同时采用。独立平面不自动保证故障时作业继续，端侧与通信库必须支持检测和恢复。[5]

4.1 协议选择

InfiniBand 是 IBTA 标准化的互联体系；RoCEv2 在以太网 IP/UDP 上承载 RDMA；Spectrum-X 是厂商以太网平台而非与 RoCE 平行的传输标准。选择应比较指定设备代际、拓扑、规模、软件兼容、故障表现和全生命周期成本，不宜给出脱离条件的固定时延排名或价格倍数。传统 TCP/IP 适合多种业务与管理流量；是否需要为存储网使用 RDMA 取决于存储协议、实现与实测。

5. 核心技术原理：从传输到拥塞

5.1 RDMA 与端网路径

应用通过通信库提交操作，注册内存并由 RNIC 使用队列与 DMA 搬运数据，减少 CPU 对数据复制的参与；是否可直接访问 GPU 显存取决于 GPU、驱动、NIC、PCIe/IOMMU 和通信库共同支持。RoCEv2 可跨 IP 网络，但需要端侧和网络一致的路由、MTU、优先级、拥塞与故障配置。卡上标称速率不代表 GPU 到 GPU 的有效速率。

5.2 ECN、拥塞控制与 PFC

多源同时向一端发送时，出口队列可能积累。ECN 可在队列拥塞前标记报文，接收端反馈后发送端依算法降速；PFC 为特定优先级在相邻链路上暂停，是缓冲保护而非端到端速率控制。持续 PFC 可能造成队头阻塞和拥塞扩散，不保证绝对零丢包。需统一 DSCP/PCP→设备内部队列映射、ECN 策略、PFC headroom、NIC 反馈与恢复，并观察队列、标记、pause、丢包及重传。[6] [7]

headroom 粗估 ≥ 链路速率 × 停止生效时间 + 管线及帧余量。200G × 5 μs ÷ 8 ＝ 125 kB，仅为时间项，不能直接作为设备配置值。

IP Traffic Class/TOS 是 DSCP 6 位与 ECN 2 位组成的字节；设备内部 TC/队列和 VLAN PCP 是不同字段。ECMP 按哈希选择路径，可能发生流碰撞；自适应路径和逐包分散要权衡乱序及端侧支持。NCCL 的 NCCL_IB_HCA、NCCL_CROSS_NIC 等依版本和拓扑生效，不能假定其他厂商通信库支持同名参数。[8]

6. 端口、收敛比、CPU/GPU 与光学约束

6.1 从端点到交换机

服务器数 N＝⌈目标 GPU 数 G ÷ 每台 GPU 数 g⌉。
网络端点链路 L＝Σ（每类设备台数 × 每台启用端口数）。
若每个物理口可拆 b 个有效支路，下行物理口 D＝⌈L/b⌉；Leaf 台数 ≥ ⌈D ÷ 每台可用下行口⌉。
实际需逐台处理速率、端口组、冗余、双归属、其他端点及取整；Spine 对端口、链路分布与故障容量另计。

收敛比在本文统一定义为 Leaf 下行单向标称带宽 ÷ 上联单向标称带宽。64×200G 下行与 32×400G 上联同为 12.8 Tb/s，故为 1:1；若只接入 40×200G，下行已用线速为 8 Tb/s，已接入下行/上联为 0.625:1。满配规划和当前使用是不同口径；1:1 也不保证所有负载均能达到线速。

6.2 CPU/GPU 与 PCIe 拓扑

CPU:GPU 没有跨平台固定最佳比。按每 GPU 每秒样本/请求需要的预处理、分词、数据搬运、进程及内存带宽推算 CPU，并预留 OS/通信与故障余量。映射 GPU、NIC 与 NVMe 到 CPU socket、PCIe root complex 和 NUMA：若大量流量跨 socket，可能增加时延、争用 CPU 互联；同时核对每个 PCIe 上行的汇聚带宽、插槽和功率。应以 CPU 利用率、数据等待和 GPU 空闲时间验证，而不是仅计算核心数量。

6.3 光模块和线缆

选择首先确认所需速率、距离和链路结构，再确认 PHY（如 SR/DR/FR）、多模或单模、模块封装、FEC 与两端兼容。普通可插拔直连通常每条链路两只模块、一条线缆；AOC/DAC 属整缆，不应重复加两只模块。分拆物理口按模块数计，支路按逻辑链路计；MPO 根数、连接器和纤芯数不同。400G-SR8 可用于兼容实现的 2×200G-SR4 分支，但必须由交换机、模块及线缆兼容矩阵确认；不得凭外观判定。[9]

链路光预算：发射功率 − 接收灵敏度 ≥ 线路衰减 + 配线架/连接器/熔接损耗 + 工程余量；同时核查接收过载、距离、介质与极性。最终按逐链路实际走线路径确定长度。

7. 案例 A：双节点 16 GPU 网络拓扑与计数

教学假设：2 台服务器各 8 GPU、8 个独立 200G 计算端口；1 台交换机有 64 个 400G 物理口，假定每口支持作为单个 200G 使用。每条链路两端为独立 200G 光模块、1 条光缆。此例仅计算计算网，不包含独立存储、业务或带外网络。

每台服务器共有 8×200G＝1.6 Tb/s 标称单向接入，两个服务器之间的实际通信还受 GPU↔NIC 映射、PCIe、软件及交换机限制。单交换机失效会使计算网络中断；物理口模式、模块兼容、FEC 和 GPU–NIC 亲和性均需验证。另需实际规划 BMC 与业务管理路径。

8. 案例 B：70 台 GPU 服务器的网络与物料设计

统一假设：70 台服务器，每台 8 个 200G 计算口、2 个 100G 存储口、2 个 25G 业务/管理口、暂按 1 个 BMC；8 台计算 Leaf 各 128×400G，每台 64 口上联；4 台存储 Leaf 各提供 64×100G 下行及 16×400G 上联；6 台管理 Leaf 各 48×25G；3 台带外交换机按 32 台服务器/台规划。所有端口能力和兼容性均为案例假设。

8.1 逐项推导

  1. 计算端点 70×8＝560 条 200G。若 400G 物理口支持拆分为 2×200G，则 Leaf 下行口为 560÷2＝280 个，均衡分配为 35 个/台。
  2. 每 Leaf 另用 64 个 400G 口上联，占用 35＋64＝99/128 口；当前下行 70×200G＝14T，上联 64×400G＝25.6T，比例约 0.547:1；满配 64 个下行物理口才是 1:1。

9. 从模型、SLO 和 GPU 规格推导集群的 SOP

步骤 1：明确输入与验收契约

确认模型参数、架构与精度、输入/输出长度分布、训练数据量或推理请求到达分布、目标质量；明确 TTFT/TPOT 的分位数和成功率、吞吐、训练完成期限、同时作业数量、可用性及维护窗口。GPU 需提供可用显存、目标精度支持、实测算力/带宽、节点互联及 NIC；还需价格、机柜功耗与软件兼容。

步骤 2：显存和最小并行度

推理每副本显存需求 ≈ 模型权重 + KV Cache + 激活/工作区 + 通信缓冲 + 框架开销 + 安全余量。
权重粗估＝参数量 × 每参数字节数；KV 粗估＝2 × 层数 × KV 头数 × 头维度 × 有效缓存 token 数 × 每元素字节数（按实际分片、数据类型和实现修正）。
训练显存还包括梯度、优化器状态、激活、临时缓冲和通信；ZeRO/混合精度/重计算会改变分布，不宜使用固定字节常数作为最终结果。

按单卡可用显存得到初始 GPU 下界，再根据 GPU 间互联、TP/PP/EP 的可用组合和整机卡数取整；显存能装下只是可运行的必要条件，并不证明满足时延。长上下文 KV、批量和碎片必须以真实框架实测。

步骤 3：按训练期限或推理容量求规模

训练：估算目标训练总 FLOP、可用训练窗口、每卡目标精度峰值及可达到的有效利用率 η。初步 GPU 数 ≥ 总 FLOP ÷（秒数 × 单卡峰值 FLOP/s × η）；η 必须以同模型/规模试验估计，并随并行度变化，不能无条件固定。再比较数据供给、通信、故障恢复、checkpoint 时间，按每机卡数及故障预留取整。学习质量和目标 token 总数应由算法团队确认。

推理：在目标输入/输出长度和 SLO 下压测一个副本得到稳定承载能力 q（请求/秒），所需副本数 ≥ ⌈峰值请求率/q⌉，再考虑突发、安全裕量和故障切换；GPU 总数＝副本数×每副本 GPU 数，按节点与拓扑放置。若单副本 q 无法同时满足 P95/P99 时延，不能简单按理论 token/s 除法计算。工作负载混合与排队会改变 q，应测完整服务栈。

算例，仅用于说明：假设显存分析后一个推理副本需要 4 GPU；在指定长度分布及 TTFT/TPOT P95 目标下，单副本稳定承载 5 请求/s；峰值 18 请求/s，则至少 ⌈18/5⌉＝4 个副本。若要求任一副本故障后仍承载峰值，需至少 5 个副本，共 20 GPU；每机 8 GPU 时容量下界为 3 台，但还要解决副本跨机放置、单机故障同时失去几个副本的问题，故 3 台不自动满足故障目标。

步骤 4：从并行图推导网络

对每个并行组记录 GPU/rank、通信模式、消息量、频次、可重叠窗口和峰值并发；先将高频 TP 放入快速域，再映射 DP、PP、EP 的跨节点路径。每节点平均所需有效带宽 ≥ 窗口内发送字节×8÷窗口时间；网络割面需求取同一时刻跨该割面的所有流之和，按实测利用率、冲突和故障余量设计。对 AllToAll 和 checkpoint 还需检验最热接收端与突发队列。端口速率只是上界。

步骤 5：形成四网及物料

建立全设备端口矩阵，逐网络计算端点、每台 Leaf 上下行、Spine 对端口与拓扑；校验单链路、单交换机及单机柜故障后的容量。按逐链路的两端规格和线缆路由生成 BOM，再加备件；分别完成 CPU、PCIe、存储吞吐、机柜功率、制冷与安全评审。

步骤 6：逐层实测与迭代

依次测试物理光功率/FEC → NIC 单/多流 → 跨 Leaf 及拥塞 → 集合通信多消息尺寸 → 存储 → 实际模型 → 长稳与故障恢复。记录版本、拓扑、负载、P50/P95/P99、错误率、GPU 利用率和资源消耗。先签署测试负载和阈值，再以原始日志复核；未达到 SLO 时区分显存、计算、CPU、存储、网络或调度瓶颈，调整后重新验证。

技术原理深化：从模型张量到链路和容量

1. GPU 训练为什么会产生通信

Transformer 的权重、输入激活和梯度都是张量。单卡放不下或计算时间过长时，将张量、层、样本或专家拆到不同 GPU；拆分改变了每一步需要交换的数据，而不仅仅是把 FLOP 平均分配。

操作输入与输出的区别网络含义
AllReduce每个 rank 输入同形状数据并得到归约后的完整结果。数据并行梯度同步；全体参与，完成时间易受最慢 rank 影响。
ReduceScatter归约所有输入后，每个 rank 只获得结果的一片。用于梯度/优化器分片；数据布局须与后续更新一致。
AllGather每个 rank 提供一片，所有 rank 获得拼接后的完整结果。按需恢复参数或激活；输出总大小与输入片大小的定义必须在测试中写清。
AllToAll每个 rank 向其他 rank 分发不同的数据块。MoE 分发与回收；专家负载倾斜可能使单目的口成为瓶颈。
Send / Receive指定源和目的之间的数据传输。流水线相邻阶段传递激活；分配不当会产生流水气泡。

以四个 rank 的 AllReduce 为例，将大小 S 均分四片，ring 的 ReduceScatter 经三轮归约，随后 AllGather 三轮传播；每节点发送 2×3/4×S＝1.5S、接收同量。其他树、分层算法或网络卸载的数据路径不同。Megatron 分布式优化器示例先 ReduceScatter 梯度、各 rank 更新自己的参数分片，再 AllGather 更新后参数；通信与计算可按 bucket 重叠，但重叠时间不能简单从通信时间完全扣除。官方实现说明

2. 节点内拓扑：为什么 8 张 200G 网卡未必得到 1.6T 有效带宽

每张 GPU 经 PCIe switch 或 CPU root complex 连接网卡；若 GPU 到 NIC 跨 CPU socket，数据可能经过 CPU 间互联，形成共享瓶颈。应绘制 GPU → PCIe switch → NIC → CPU/NUMA 的实际矩阵，并标注每个上行链路的方向、速率和共享关系。200G 端口单向线速是 25 GB/s；8 个口的名义总和 200 GB/s 不代表某一 GPU 或 PCIe 上行能承担此流量。PCIe 链路带宽、GPU 直访、IOMMU、NIC DMA、主机内存路径和通信库选路共同约束有效吞吐。

验证时分别做 GPU↔本机 GPU、主机内存↔NIC、GPU↔近端 NIC、GPU↔远端 NIC，以及并发多流测试；对照 PCIe 拓扑与 NUMA 绑核，避免把单口满速误当整机满速。GPUDirect 类能力需要硬件、驱动和框架端到端支持，不能由 RNIC 规格单独推断。

3. RoCE 数据包、排队与反馈闭环

应用提交内存操作后，RNIC 将数据组织为 RDMA 操作并以 RoCEv2 经 UDP/IP 承载。网络依 DSCP/PCP 将包分类到内部队列：发送端标记 → 交换机信任字段并映射优先级/队列 → ECN 阈值触发标记 → 接收端识别标记并产生拥塞反馈 → 发送端按具体算法降低/恢复发送速率。ECN、CNP、发送端算法和队列配置必须配套。

PFC 是逐跳、逐优先级的暂停机制：当缓冲达到 XOFF，上游停止该优先级，低于 XON 后恢复；停止并非瞬时，触发后仍有链路和处理管线中的数据到达，因此需要 headroom。PFC 不能代替端到端拥塞控制，暂停可能传播；watchdog 解除持续暂停时可能丢弃报文，是否影响作业由产品实现和恢复机制决定。相关行为应通过 NIC 计数器与交换机队列、ECN、CNP、pause 和 discard 时间序列一起验证。RoCE 拥塞反馈机制

字段示例：DSCP 占 IP 字段高 6 位，ECN 占低 2 位；DSCP=26、ECN=2 时，8 位字段＝26×4＋2＝106。VLAN PCP、IP 字段和交换机内部队列编号不是同一概念；具体 DSCP 值与 NIC/交换机匹配，不应照搬。

MTU 增大可以减少每字节包头与处理次数，但会改变序列化延迟、丢包重传粒度和缓存需求；两端及所有路径必须支持相应 MTU。FEC 能纠正部分物理层误码，需两端模式兼容；持续增长的 FEC 修正、不可纠正错误或 CRC 需结合光功率、温度及链路状态排障。

4. Clos 容量、割面和故障态

每台 Leaf 的下行和上联相等只说明该 Leaf 的标称容量匹配。还要检验任意流量割面、Spine 端口和交换芯片内部转发能力。例如 8 台 Leaf，每台 64×400G 上联，合计 512 条；4 台 Spine 均分时，每对 Leaf–Spine 为 16 条，每台 Spine 8×16＝128 口。若单 Spine 故障，每 Leaf 剩 48×400G＝19.2T，上联减少 25%；若业务要求故障时仍支持 25.6T，则需要不同规模和端口预留，不能仅凭 ECMP 达到。

ECMP 通常对流哈希，不保证每条链路均匀；同一出口 incast 或单流哈希碰撞会使局部拥塞，即使全网平均利用率不高。设计检查应包括正常/故障下的每对设备链路矩阵、最坏业务放置、单目的端口和 oversubscription，并以 bisection、单热点、多作业竞争与故障测试证明。

5. 光学规格与物料链路闭合

光模块接口封装（如 QSFP-DD）不等于物理层标准（如 SR8、DR4）；相同 400G 速率也可能使用不同波长、单模/多模、芯数及距离。需要明确模块 SKU、设备端口模式、FEC、分支支持、线缆芯位、MPO/LC、极性及长度。光纤通道由设备口—模块—跳线—配线架—干线—跳线—模块—设备口组成；链路数不等于每段跳线数。验收记录各段插损、两端光功率和误码，不仅看端口是否 Up。

6. 存储吞吐、CPU 和机房资源

数据读取目标＝并发任务数 × 每任务样本数/s × 平均实际读取字节/样本；按命中率、预取和压缩后的真实存储请求修正。
checkpoint 平均写入需求＝同时写入总字节数 ÷ 允许窗口；实际吞吐上限＝客户端、网络割面、存储 NIC、介质及文件系统能力中的最小值。

例如 8 个训练作业各需 5 GB/s 的后端持续读，合计 40 GB/s＝320 Gbit/s；这只是平均需求，不能代替启动风暴、元数据和重建期间的容量测试。按每 GPU 的数据预处理 CPU 时间和每秒样本量累加核心需求，并为系统、通信和突发留余量；CPU:GPU 比不是通用常量。整机实测功率乘节点数后考虑冗余电源策略、PDU 和冷却，不能把所有电源模块铭牌简单相加当作真实负载。

网络架构与技术演进：设计深化

理解集群网络时，可以从互联范围、通信语义和网络职能三个维度切入：互联范围讨论 Scale-up / Scale-out / Scale-across；通信语义区分远端内存访问与消息传输；网络职能区分计算、存储、业务及带外。三个维度不能互相替代，也不意味着每个维度必须独占一套设备。

1. Scale-up：从 GPU 间传数据到远端内存语义

Scale-up 目标是在一个高带宽互联域中让多个加速器协同。点对点或交换式互联可以支持设备间数据搬运；部分架构还提供远端 load/store、atomic 等操作。远端可寻址不等于所有显存自动形成一致、等速的共享内存：需要区分地址映射、访问权限、一致性域、内存屏障与可见性，实际由硬件、驱动和编程模型共同规定。对于小消息，协议启动和同步延迟重要；对于大块数据，聚合带宽、并发和拥塞更重要。

设计时先画出 GPU/GPU 与 GPU/NIC 的路径和带宽矩阵，把层内高频 TP 等通信尽量放入快互联域，再考虑跨域通信。是否存在 GPU→另一 GPU→NIC 的转发路径，必须由通信库、设备拓扑和可观测数据证明。UALink 联盟公开资料将 UALink 200G 1.0 定义为面向加速器和交换机的 Scale-up 互联规范，并描述最高 1,024 个加速器的规范范围；这不是任何具体设备的已交付规模或性能保证。UALink 官方规范目录

2. Scale-out：Clos、Rail 与双平面的选择方法

方案通信和设备关系适用条件与风险
单层 Rail-only同一编号的 NIC 接入对应交换机或独立网络；不同 Rail 不直接互通。交换机可容纳所有同轨端点、集合通信能利用同轨通信和节点内互联时较简单；不规则分配、跨轨流量和故障后的替代路径须实测。
Rail-aligned Clos同轨端点集中到对应 Leaf，多个 Leaf 通过 Spine 形成更大网络。提高同轨局部性并扩容；若共享 Spine，则各 Rail 不是完全独立故障域。
双 Plane + Rail每个相关端点同时具有到两个独立网络平面的路径；每个平面内可再按 Rail 分组。需校核端口、链路、供电及软件失败处理。双 Plane 容量是否对半、故障后是否继续，取决于实际方案，不能只看两条网线。
Dragonfly 类交换设备分组，组内/组间按特定规则连线；通过较少网络层次扩展。须按拓扑与流量矩阵核算全局链路、路径选择、热点和故障域；不应笼统认定其一定比 Clos 更便宜或更快。

在已有端口约束下，可先设计连接矩阵 M[i,j]：第 i 台 Leaf 到第 j 台 Spine 的链路数；检查每行之和是否为 Leaf 上联数、每列之和是否不超过 Spine 可用口，并计算单 Spine 失效后各 Leaf 剩余带宽。端点也要逐个映射到 Leaf、NIC、GPU、CPU socket 和机柜，以免形式上均衡、实际却共享同一个 PCIe 或供电故障域。

3. 链路可靠性：FEC、LLR、CBFC 与端到端恢复

机制保护范围与作用工程边界
FEC物理层加入冗余，纠正能力范围内的误码。不能消除所有链路故障；关注纠错与不可纠正计数、两端配置及延迟。
LLR：链路层重传由相邻链路设备检测并重发特定受损/丢失的数据，缩短某些错误的恢复范围。依赖相邻两端支持和协商；不会代替端到端可靠性或自动消除拥塞。
CBFC：基于信用的流控接收端向相邻发送端通告可用接收缓冲信用，发送端按信用发送。是与 PFC 不同的逐链路机制，依赖双方能力、缓存与配置；不表示全网没有队列或热点。
端到端重试 / 作业恢复应对超出单链路保护范围的丢包或节点故障。重试粒度、超时、通信库和 checkpoint 行为依实现；网络恢复并不保证原训练进程继续。

UEC 对 LLR、CBFC 等描述为可选链路能力；两端必须支持并启用相同功能。选型时需将可选能力、固件版本、兼容矩阵与错误计数纳入验收。UE 1.0.2 链路层规范

4. 光互联：可插拔、LPO、NPO、CPO 与 OCS 解决不同问题

技术解决的问题设计和运维要核对
可插拔光模块交换机/NIC 接口处完成电光转换，按距离和 PHY 灵活选型。模块、FEC、线缆兼容，功耗、热插拔和备件；高速模块常包含信号处理功能，依型号而异。
LPO / NPO / CPOLPO 强调线性光链路；NPO/CPO 分别将光引擎向交换芯片靠近或共封装，以改善电链路距离与功耗。不是同一代际的必然替换关系。关注链路预算、可维护性、光源、封装、兼容性及系统级功耗，不套用固定降幅。
OCS 光路交换在光域建立端口间光路，可重构物理连接；数据通过既有光路时不经过传统电分组转发。光路切换有时间开销；不提供传统分组交换的队列行为。要评估流量稳定性、链路编排、故障检测、插损和恢复。

光路重构可服务于拓扑和容量调度，但需要软件控制与业务通信图配合；是否节省成本、功耗或交换层级依拓扑、设备和运维边界。Google Jupiter 的论文展示了 OCS 与软件定义网络结合进行数据中心网络重构的实例，不应将该系统的表现直接推广到任意 AI 集群。Jupiter Evolving 论文

5. Scale-across：为何长距离需要重新设计

长距离链路的传播时延增加，带宽时延积 BDP＝带宽×往返时间。例如 800 Gbit/s、RTT＝1 ms 时，BDP＝800 Mbit＝100 MB；这只是链路中的数据量级，不等于交换机必须配置 100 MB 缓存，也不代表一次丢包必然重传整个窗口。拥塞反馈更慢、错误恢复更昂贵，逐跳暂停不能被简单理解为适合跨整个广域网的无损方案。

模型并行应考虑流量强度和计算/通信重叠：将需要频繁同步的组尽量放在低延迟域，跨中心使用对时延更可容忍的分组或流水划分；同时核算链路容量、加密、光传输、数据合规、故障恢复和跨域作业 SLO。不同模型的最佳并行方式必须通过工作负载测试确定，不存在普适的“某并行方式必然跨域”。

6. 端网协同与可观测闭环

将应用 step 时间、rank 放置、集合通信耗时与 NIC 重传、队列水位、ECN、PFC、链路/FEC 计数、光功率和交换机端口利用率按统一时间关联，才能区分“算子慢”“端口慢”“拥塞”“存储等待”和“故障重试”。集中化配置、遥测和自动校线能降低运维复杂度，但自动生成的配置仍需版本管理、变更验证和回滚。

优化流程：①确定正常基线和业务指标；②采集慢 step 与对应 rank/NIC/队列；③通过单流、多流、热点及跨 Leaf 测试定位；④仅改变一个因素验证；⑤用目标模型与故障场景回归。DPU 或智能网卡可以卸载部分网络、安全和存储功能，但具体卸载能力、CPU 节省量及端到端性能应以对应产品实测为准。

网络设计实操：约束清单、计算表与评审门槛

使用顺序：先确定每张网络承担什么流量，再计算端点及上下联带宽；接着按设备端口组和故障域落位；最后逐链路核对光模块、光纤与采购范围。所有速率统一为单向 Gbit/s，应用吞吐另用 GB/s；1 GB/s＝8 Gbit/s，线速不等于有效业务吞吐。

二、不同网络的带宽如何选：先需求、再端口

网络带宽需求如何取得下行与上行如何检查容易遗漏
计算 / 参数面按目标并行策略测每 rank 的 AllReduce/AllGather/AllToAll/P2P 消息大小、峰值并发和可重叠窗口；确定目标任务通信占比及 P95/P99。每 GPU/NIC 的有效需求、每 Leaf 接入与上联、跨 Leaf 割面和故障后容量都要算；端口速率按工作负载和可用 NIC/PCIe 能力选择。TP 高频小消息与 DP 大消息不能只看同一项平均带宽；单轨故障能否继续由端侧和通信库决定。
存储 / 样本面训练持续读取、启动热身、checkpoint 并发写入、恢复及存储重建分别算；按存储池分别测读写能力。客户端口 → Host Leaf 上联 → 网络割面 → Disk Leaf → 存储 NIC → 介质，取实际同时工作的瓶颈；分别计算读取和写入方向。GPU 侧上联很大不等于存储池能供给；对象存储和并行文件系统不能随意合并为一个吞吐池。
业务 / 带内管理测入口请求、数据导入导出、镜像分发、日志/监控、平台控制的同时峰值及安全策略。服务器→接入 Leaf、Leaf→核心、核心→出口逐级对照；根据业务可接受的拥塞、故障状态和流量共时率选速率及收敛比。25G/100G 只是可选速率，不是所有项目通用标准；控制节点、网关和防火墙吞吐也可能是瓶颈。
带外管理统计所有服务器 BMC、交换机管理口和安全设备的并发管理流量，核实端口速率/介质与隔离要求。端点口、交换机管理上联、跳板访问和故障域逐一分配；通常按低带宽管理流量设计，但以现场设备和需求为准。单 BMC 口即使上联冗余也不是服务器接入双归属；铜缆、带外上联不能遗漏。
不要从一张速率推荐表直接下单：同样是 200G/400G，端口数量、消息形态、网络比例、NIC 与软件栈不同，业务效果可能不同。需要先给出目标负载下的吞吐与延迟，再以受支持的产品组合和 PoC 确定速率。

三、逐层设计：端口、上联和 Spine

步骤 1｜端点端口。对网络 k 按设备类型求和：逻辑端点数 Eₖ＝Σ（设备数量 Nᵢ × 每台启用端口 pᵢₖ）。把独立端口、一个端口拆出的支路和未启用的预留端口分开；同一服务器的两个端点是否分配不同 Leaf，要在连接表中明确。

步骤 2｜Leaf 下行。若每个适配的物理端口可拆 b 个支路，理论下行口数为 ⌈Eₖ/b⌉；再按每台设备、端口组、Leaf 数及双归属分别取整，不应只对全网求一次上整。单台 Leaf 必须满足：已用下行物理口＋上联物理口＋互联/管理占口＋扩容预留 ≤ 对应可用端口组容量。

步骤 3｜上联与收敛比。对每台 Leaf，计算 D＝Σ已接入端点单向线速，U＝Σ上联单向线速。本文收敛比为 D/U；如需当前业务容量，还须根据并发和流向计算实际跨 Leaf 流量。以 U ≥ 目标跨 Leaf 峰值有效速率 ÷ 假设有效利用率做初估，再检查合同要求的线速收敛比与故障态。有效利用率须来自相似场景的测量，不能默认某个百分比。

步骤 4｜Spine。计算各 Leaf 的上联条数总和，Spine 侧必须有同数可用物理端口。构造 Leaf×Spine 连接矩阵，每行等于该 Leaf 实际上联数，每列不超过该 Spine 可用端口；同时检查各链路速率、交换芯片带宽、等价路径和扩容余量。网络整体还需核算跨割面的同时通信量，不能仅看一台 Leaf 的端口。

步骤 5｜故障态。分别从矩阵中删去一条上联、一台 Spine、一台 Leaf 或整个平面，重算各端点可达性和可用带宽。交换机口数满足不代表通信库能在故障后继续；作业是否中断需实测。不要将业务、计算、存储共享的电源/机柜误认为独立故障域。

四、上下游速率不同：逐段算，而不是取一个最大值

定义方向：下行指交换机朝服务器/存储端点，上行指 Leaf 朝 Spine/核心；读写业务的实际发送方向可能相反。全双工接口的发送和接收各有各自的单向速率，不能把双向之和当作单向可用带宽。

段位设计约束需要检查
GPU ↔ NIC / CPU ↔ NICNIC 端口合计速率不能忽略 GPU/NIC 的 PCIe 上行共享、NUMA、CPU 间互联和 DMA 路径。多 NIC 同时工作的聚合带宽、跨 socket 流量、GPU 直访支持和实测吞吐。
端点 ↔ Leaf每个端点的单口速率和条数由该设备实际能力与所需有效吞吐决定。速率/FEC/模块、端点端口对应 Leaf 和故障域；链路任一端不兼容即无法按预期运行。
Leaf ↔ Spine每台上联速率之和应满足目标跨 Leaf 流量及所选收敛比；两端速率必须协商或按支持的 breakout 兼容。相同方向累计容量、Spine 对端口、ECMP 和故障后剩余容量；同 Leaf 内流量不一定经过 Spine。
存储交换机 ↔ 存储节点聚合业务吞吐 ≤ 相关存储节点 NIC、文件系统和介质的可持续能力。单目的热点、各存储池独立容量、数据重建及 checkpoint 并发；链路空闲不表示后端介质不忙。

例：某 Leaf 接 32 条 200G 端点链路，下行额定 6.4 Tb/s；16 条 400G 上联也为 6.4 Tb/s，规划比 1:1。若 4 台 Spine 等分、每台承接 4 条，损失一台后仅剩 12×400G＝4.8 Tb/s，上联为原来的 75%，此时下行/上联约 1.33:1；如故障后仍要求 6.4T 上联，应预留更多且独立的链路/Spine，并检查设备端口及内部容量。

五、光模块与光纤：从逐条链路生成 BOM

核算项实操方法交付结果
① 每条链路两端登记 A/Z 设备、物理口/逻辑子口、方向、速率、接口、距离与对端；一根线缆组装件可能承载多个逻辑支路。端口连接表与物理口使用表。
② 模块规格对每段确认标准/PHY、波长、lane、SR/DR/FR、单/多模、封装、FEC、设备模块白名单及两端兼容。双方可用的具体模块 SKU 和版本，不仅是“400G 模块”。
③ 线缆与布线按链路实际路径列出直连线、配线架跳线、主干、连接器类型/性别、极性、纤芯、长度、损耗和余量。每段线缆 SKU、数量及链路预算；不同物理段分开计数。
④ 汇总在用模块普通可插拔点对点：1 条链路＝2 个模块；兼容的 1×400G→2×200G：1 个 400G 端＋2 个 200G 端＝3 个模块、2 个逻辑链路；AOC/DAC 整缆按产品形态计。按速率/PHY、设备侧与端点侧分别汇总的安装数量。
⑤ 去重与备件标记服务器、交换机随设备自带模块；从安装量减去已包含部分，再加合同规定的备件，分别列出并避免重复。安装量、随货量、需另购量、备件量四列；保留采购与厂商确认依据。

示例：70 台各 8×200G，共 560 条计算下行支路；若设备和 SR8 模块均支持 400G→2×200G，需 Leaf 侧 280 个 400G 模块、服务器侧 560 个 200G 模块及 280 根分支组件。此数量不含配线架拆段、备件和上联；若端口组、模块或光学不能兼容，就必须另选方案、重算数量。链路损耗预算应留工程余量，并检查最大接收功率及距离，不应只验证模块名称。

集群建设实操：机房、供配电、制冷与运维

工程边界：本节用于需求测算与专业评审，不替代土建、结构、电气、暖通、消防和给排水的设计、审批与验收。供电、承重、制冷及消防参数必须结合设备厂家设计数据、当地条件及适用的现行规范，由有资质的专业单位确认；以下数值均为教学假设。

建设顺序应从“有多少台服务器”扩展为：业务与可用性目标 → 设备功率和重量 → 机柜分布 → 供电和散热 → 土建/水路/消防 → 安装联调 → 运维保障。机房容量不是只看总电力：单机柜功率、配电支路、冷量、楼板点载荷和故障状态中的任何一项不足，都可能限制上架数量或网络布局。

一、先确定建设边界和设计输入

类别需收集的输入必须输出的结果

二、机柜与空间：先画布局，再核算供冷布线

按照服务器尺寸、U 位、厂家规定的进出风方向、维护抽拉空间和机柜承重安排上架；把 GPU 服务器、存储、网络、CDU/歧管、PDU、配线架和管理设备一起放入平面图。明确冷热通道、封闭方案、气流短路和回风路径；液冷仍可能存在 CPU、内存、网卡、电源和未覆盖 GPU 部件的空气散热。机柜功率密度不均会导致局部热点，不能只按全机房平均值设计。

由结构专业同时核查均布荷载、局部集中/点荷载、机柜脚轮或底座、活动地板及下方结构、运输吊装路线；机柜重量须含满配服务器、线缆、导轨、PDU、冷却液、歧管及安装余量。空间规划还要预留设备检修、消防通道、漏液收集和扩容，机柜数量应在 U 位、重量、功率和冷量多项限制中取最严格者。

三、供配电：从 IT 输入功率到故障态支路容量

先按每台设备同时工作的设计输入功率汇总 IT 负载，再按机柜和配电支路分配。服务器电源的额定功率、N+1 电源数量不是整机实耗；但不能只取低负载平均值，需让厂家提供最大持续、启动浪涌/瞬态和故障降额信息。交换机、存储、管理设备及机柜内辅助设备不可遗漏。

IT 设计功率 P_IT ＝ Σ（每类设备数量 × 设计同时输入功率）＋ 已计入 IT 边界的网络/存储等。
由功率估算电流：单相近似 I＝P/(U×PF)；三相平衡近似 I＝P/(√3×U线×PF)。实际回路选择仍需专业设计单位考虑线缆、保护、谐波、环境、启动瞬态、相不平衡与法规。
稳定运行的设施总能耗估算：E_total≈PUE×E_IT；PUE 是同一计量边界和时间段的能耗比，不能直接替代变压器、UPS、发电机、冷机或支路容量设计。

冗余设计：N 是满足设计负载的工作能力，N+1 是额外冗余一个容量单元，2N 是两套各自可承载设计负载的路径或系统；具体必须说明指 UPS、配电、冷机还是端到端系统。A/B 两路正常各带 50% 并不自动可承受一路故障：必须核验剩余 UPS、配电、PDU、插座、电源及保护均可在允许时间内承担故障后的实际负荷，且两路没有未识别的共同故障点。UPS、发电机切换、蓄电池续航与带载维护按业务目标验证。

例如只为说明计算方法：三相 400 V、功率因数 0.95、40 kW 负载且理想平衡时，电流约 40,000/(√3×400×0.95)＝60.8 A；这是理论电流而不是断路器或电缆选型结果，禁止直接据此施工。GB 55024-2022 发布公告明确该规范为强制性工程建设规范，具体适用条款和版本应由专业单位核验。

四、制冷与液冷：热从哪里来、经过哪里走

冷板液冷、后门换热和浸没式等方案在设备接口、传热介质、维护与安全要求上不同。至少核对：设备热捕获比例、进出口温度/压差/流量范围、液体水质和材料兼容、过滤与腐蚀控制、接头/快接、歧管和 CDU 容量、泄漏检测、维护排液、断流保护及设施侧散热。冷量通常以 kW 表示，1 kW 电功率在稳态下最终大致对应 1 kW 热量，但热量会分配到不同流路，不能把全部负荷重复算进风冷和液冷。

液体散热近似：Q(kW)＝ρ(kg/m³) × cₚ(kJ/kg·K) × 流量(m³/s) × ΔT(K)。
近似按常温水 ρ＝1000、cₚ＝4.18，则流量(m³/h)≈0.861×Q(kW)/ΔT(℃)。其他介质及实际温度须采用实际物性；该公式不包含压降、泵扬程和冗余校核。

例如某液冷回路要排出 100 kW、供回水温差假设 5℃，理论水流量约 0.861×100/5＝17.2 m³/h；这不是 CDU 选型结果。还须校核每个支路最低流量、供水温度、压降、换热端差、泵工况、温湿度和失效模式。机房空气温湿度按设备允许条件及项目设计确定，尤其需结合露点、结露风险与厂家要求，不应直接套用通用温度数字。美国能源部液冷与设施水侧说明

七、运维组织：不只是服务器上电

按设施、网络、存储、GPU/服务器、平台、模型业务和安全建立责任矩阵与统一告警：设施侧监测电能、UPS、电池、PDU、温湿度、漏液、CDU 流量/温压；IT 侧监测 GPU 温度/错误、节点健康、链路 FEC、ECN/PFC、存储、作业 step 和检查点。所有监测统一时钟、资产编号及机柜/配电/网络拓扑，便于把“慢训练”追溯到具体电源、冷却、网卡或设备。

建立容量与备件计划、7×24 值守或明确的响应 SLA、故障分级和升级联系人；制定服务器/光模块/泵/滤芯等备件周转、固件版本矩阵、变更审批和回滚、应急断电、漏液隔离、断流降载及任务恢复预案。跨设施和 IT 的操作要先明确授权：例如冷却异常时先按厂家/机房应急规程保护人员与设备，再协调任务迁移或暂停。

八、交付验收：从单设备到故障联动

  1. 设计冻结：确认分期负载、机柜布局、配电单线图、制冷水力图、消防方案、设备接口、施工及维护责任。
  2. 单系统检查：检查线缆和管路标签、绝缘/接地、漏液检测、流量/压差/温度、UPS/电池、报警和监控；测试由专业人员按批准方案执行。
  3. 分级带载：先用可控负载逐步验证供电与制冷，再上 IT 设备；记录每机柜输入、热点、供回风和供回液数据，避免设计平均值掩盖局部问题。
  4. 联动与故障：按批准的风险评估测试单路电源、UPS、泵/CDU、冷源、网络及监控告警；核对转移后的余量、保护动作和恢复，不对生产负载擅自断电或断水。
  5. 业务长稳：按代表性训练/推理负载验证稳定运行、GPU 降频/错误、网络与存储性能、能耗和恢复时间；签署测试边界与不通过项。
  6. 交付：形成竣工图、端口与配电/水路台账、厂家参数、测试原始记录、故障演练、运维手册、保修和备件清单。
